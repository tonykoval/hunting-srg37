Chapter 11 · Part III Tools & Reproducibility

Every attack in this book is packaged to re-run. Two Docker images, one baked-in catalog, a dozen scripts, and three data files. The standard of the project is that any claim here can be checked by pulling an image and running one command.

11.5   Reproduce a result

# Confirm the catalog baseline (Paley(37) is graph #1, so: DUPLICATE)
docker run --rm tonykoval/srg37-hunt iso-compare /work/data/sr371889.g6

# Re-run the fast, definitive switching negative (~140 s)
docker run --rm -v "$(pwd)/out:/work/out" tonykoval/srg37-hunt \
    gm-batch --cell-sizes 4 --max-per-size 500 --out-dir /work/out/gm

# Generate fresh unaccounted neighbour targets, then attempt extension
docker run --rm -v "$(pwd)/out:/work/out" tonykoval/srg37-hunt \
    unaccounted-extension --neighbour-g6 /work/out/unaccounted_big.g6 \
    --extension-time 1800 --max-graphs 500
A logging caveat learned the hard way

Long runs with docker run --rm piped through tee can lose all output if the daemon restarts. Use stdbuf -oL or a direct redirect to a mounted file — nine hours of compute were lost once to exactly this.

11.6   The live two-graph campaign & the GPU finder

The converged seven-tower run (Ch 4, Ch 12) and the GPU finder (Ch 10) are fully scripted. The two-graph SMS engine is the de-caen-filter binary (CaDiCaL $+$ a bundled nauty canonicity propagator via IPASIR-UP); the campaign and its restart-safe resume are driven by: 

# One tower sub-cube (cube_size 16): exhaust, or emit a #6803 descendant
de-caen-filter --solve-two-graph-canon-cube 38 18 <idx> 16 \
    --catalog srg37_catalog.g6 --out hit.g6 --timeout 86400

# Resume after a restart WITHOUT redoing finished cubes (appends; skips EXHAUSTED)
WORKERS=8 bash scripts/srg37_resume.sh pending
bash scripts/srg37_remaining_work.sh hard      # the ~87 hard cubes to distribute
bash scripts/distribute_srg.sh srg37 pc-a:8 pc-b:8 …   # per-machine slices

# GPU stochastic-local-search finder (idle GPU), with the defect-repair move
GPU_TWOGRAPH=1 twograph-sls --cube-idx <idx> --budget-secs 3600 \
    --population 4096 --lk-depth 80 --out hits.g6   # f=0 ⇒ verify vs catalog
Restart-safe by construction

All state lives on host bind-mounts, so a container crash loses no progress; the container runs sleep infinity with the grind as a detached child. Resume with srg37_resume.sh, never run_all_towers.sh — the latter truncates the result log. Any non-empty hit.g6 is a $\#6803$ candidate: canonicalise with nauty-labelg and diff against the catalog.

11.7   How the hunt works, in plain words

Everything above assumes you already know what the machinery is for. This section assumes nothing. It is the explanation you would give a colleague on a whiteboard, in five steps.

Step 1 — What we are looking for

Exactly $6802$ strongly regular graphs with parameters $(37,18,8,9)$ are known. Nobody has proved the list is complete. So there are two prizes, and the same computation wins either one: if a $6803$rd graph exists, the search finds it; if it does not, the finished search is the proof that $6802$ is final. We cannot lose — the only question is which prize it is, and how much compute it costs.

Step 2 — Why we cannot just try all graphs

A graph on $37$ vertices is a choice of yes/no for each of the $\binom{37}{2} = 666$ possible edges: $2^{666}$ possibilities, a number with $200$ digits. No computer enumerates that. The whole craft of the campaign is shrinking the space without ever risking skipping a graph. Three shrinks do almost all the work:

  • Reformulate. Every $\mathrm{SRG}(37,18,8,9)$ sits inside a regular two-graph on 38 vertices (add one vertex, switch appropriately — Chapter 2). Searching for the two-graph is the same hunt in better coordinates: more symmetry to exploit, and a cleaner algebraic description for the solver.
  • Symmetry-break. Relabelling vertices gives "different" matrices that are the same graph. The engine carries a canonicity test that keeps exactly one labelling per graph and a full lex ordering on the rows ($37$-row lex chain), so the solver never explores two copies of the same object. This alone shrinks the space by factors in the millions.
  • Divide. What remains is cut into cubes: fix the first few edge decisions to a concrete pattern (the CE40 basis fixes $40$ of them), and each pattern becomes an independent sub-problem. The campaign's queue of $11{,}884$ roots is exactly this: $11{,}884$ disjoint boxes that together tile the whole remaining space.
The one property everything depends on

The three shrinks are sound: they discard only duplicates and impossibilities, never a potential graph. So "we searched every box and found nothing" really does mean "no new graph exists". A permanent auditor (srg37_cover_check.py) re-verifies after every merge that the boxes still tile everything — no box lost, none double-counted, none quietly skipped.

Step 3 — What happens inside one box

For each root, the engine (a SAT solver with the canonicity test wired into its inner loop) asks: does any two-graph exist with these fixed decisions? Three outcomes:

outcomemeaningwhat happens next
EXHAUSTEDthe box is empty — a machine-checkable certificate that no new graph hides therebanked in the ledger, forever
FOUNDthe solver produced a concrete graphthe drop-everything event — see Step 5
timeoutthe box is too hard as posedthe engine splits it into smaller boxes and queues the pieces (autosplit); a box that resists even at the finest split is ledgered HARD for the escalation lane

This is why the ledger — currently past $250{,}000$ lines at home plus your shards — is the search. Each line is a small theorem: "box $X$ contains nothing new." The hunt ends when the certificates tile the whole space, or the moment one box yields a graph instead.

Step 4 — Why a found graph is not yet a discovery

If a box ever yields a graph, one check remains: is it genuinely new, or a relabelling of one of the $6802$? The catalog ships with every worker pre-keyed in canonical form; iso-compare answers in seconds. Only *** NOVEL *** means the $6803$rd graph. (History recommends the caution: the 2026-07 window-search "find" turned out to be Spence #39 under a different labelling.)

Step 5 — The honest odds

The iron law of Chapter 9 cuts both ways: complete catalogs at small $v$ are the likely outcome, so the expected prize is the completeness theorem — which would close the first open case in the classification of regular two-graphs, open since 2001. But expectation is not knowledge: the only way to know is to finish, and a find would be the more spectacular ending precisely because the field expects the other one.

11.8   The distributed mode: many machines, one search

Because the boxes are independent, the search parallelises perfectly: any machine can grind any subset of the queue, and the certificates compose. As of 2026-08-04 this is packaged as a public Docker image — tonykoval/srg37-worker — that carries everything a stranger's machine needs: the audited engine, the pre-keyed catalog, a warm clause pool, and a snapshot of the full root queue ($145$ MB total).

Dealing the cards

Think of the queue as a deck of $11{,}884$ cards. With $N$ machines, machine $k$ takes every $N$-th card starting from the $k$-th — disjoint by construction, no coordination needed while running: 

> docker run -d --name srg37 \
    -e SHARD=k -e SHARDS=N \
    -v "$PWD/out:/srg37/out" \
    tonykoval/srg37-worker

Each machine works through its slice with WORKERS parallel engines (default: all cores but one), writes every verdict to out/ledger.tsv, and is restart-safe: kill the container, reboot the host, start it again — it resumes from the mounted volume, skipping every box it already certified. Sporadic crashes lose nothing: a crashed box never receives a certificate, is retried once automatically, and otherwise simply returns to the home queue at merge time. The first field deployment (an $8$-core machine, $2$ workers) ground a quarter of the entire queue — $2{,}974$ roots — in its first days at a $99.95\%$ per-root success rate.

Bringing the receipts home

Periodically each machine ships back one file: its ledger. Merging is a concatenation plus an audit: 

> cat ledger_shard1.tsv >> out/autosplit/ledger.tsv
> python3 scripts/srg37_cover_check.py        # MUST print CLEAN

Tags are globally unique, so ledgers from any number of machines compose; the cover-checker then re-proves that the union of everyone's certificates still tiles the space with nothing missing and nothing forged by a partial run. After a merge, the home queue is pruned — no machine re-grinds a box another machine already closed. If any shard's hits/ directory is ever non-empty, everything stops for Step 4 above.

Distributing the knowledge, not just the work

There is a second, subtler thing worth sharing. While solving, each engine learns: it discovers clauses — reusable facts of the form "this partial pattern can never extend to a solution" — that prune every later box it touches. These accumulate in a warm pool file per worker. The crucial soundness point: every engine runs the identical binary on the identical encoding, so a learned clause is a logical consequence of the shared problem — a shortcut discovered on one machine is valid on all of them. Like margin notes in identical copies of the same book: written in one copy, true in every copy.

Knowledge therefore circulates in epochs rather than live: 

nodes ship ledgers + pools home
   |
   v
merge ledgers -> cover-check CLEAN -> prune finished roots from the queue
merge pools   -> dedup, keep the short (strongest) clauses, cap the size
   |
   v
rebuild the image with the fresh queue + the fleet's merged pool
push as tonykoval/srg37-worker:<date>
   |
   v
every node:  docker pull  ->  next epoch starts where the FLEET left off,
             seeded with everything the fleet has learned

Two measured rules keep this honest. Pools are for the main grind only — a 2026-07 experiment showed a foreign pool turning a $3$-second escalation probe into $130{+}$ seconds (the "pool-poison" finding), so probe and escalation kits stay pool-free. And pools are trimmed each epoch: parse cost at every box start grows with pool size, so unbounded sharing would slowly tax exactly the thing it is meant to speed up.

Why this design is safe to open to strangers

A malicious or broken node cannot corrupt the search. Certificates are only claims until the cover-checker accepts the merged ledger, any claimed find is canon-checked against the catalog before belief, and a node that silently does nothing merely fails to speed things up. The worst a bad participant can do is waste their own electricity — the soundness of the final theorem rests entirely on checks run at home.

11.9   The standing invitation

The catalog, the unaccounted targets, and every attack are public. If you run path 1 or path 2 of Chapter 10 and iso-compare prints *** NOVEL ***, you have found the $6803$rd strongly regular graph on $37$ vertices. That is the whole point of writing it all down.
